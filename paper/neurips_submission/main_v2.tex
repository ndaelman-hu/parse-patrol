\title{Competence is not Performance: Where Coding Agents Actually Parse\\
Along the Language-Complexity Hierarchy}

\begin{abstract}
Agentic systems for the molecular sciences rest on an unglamorous first step: turning a
simulation's raw output into structured data by \textbf{parsing}. This is assumed to work
because a coding agent emits Turing-complete code---a claim about expressive
\emph{competence}, not realized \emph{performance} (Chomsky's distinction). We make it
measurable: on real computational-chemistry output we vary an MCP parser harness from no
support to complexity-aware, running a first sweep (159 runs, Claude Opus 4.8) that scores
success, workload, and failure modes by grammatical class. The result is not the obvious
one. Merely exposing tested parsers barely changes success, raises workload, and
\emph{introduces} silent interface failures the from-scratch baseline never produces;
what removes them---at near-baseline cost---is telling the agent where the source sits on
the language hierarchy and where each tool's power ends, while reasoning failures persist.
Realized parsing performance thus depends less on \emph{access} to tested tools than on
\emph{knowing} their power relative to the task.
\end{abstract}

\section{Introduction}

\theme{the assumption}When a coding agent is deployed in a scientific workflow, it is
commonly assumed to handle whatever data processing the workflow requires. The
underlying argument is that the agent writes code, that code is a Turing-complete
medium, and that such a medium can express any computable transformation; any
computable task should therefore be within reach. The assumption underlies the use of agents as
general-purpose connectors between scientific tools and the data they emit.

\theme{competence vs.\ performance}This conflates two notions Chomsky long ago
separated: \emph{competence}, what a system can in principle represent, and
\emph{performance}, what it reliably does \citep{chomsky1965}. The ``agents are
Turing-complete'' claim is entirely about the first. That an agent can \emph{emit} a
Turing-complete language is trivially true; and the stronger expressivity results---that
a transformer's forward pass is Turing-complete \citep{perez2021}, or that
chain-of-thought extends its reach \citep{merrill2024cot}---hold only under idealized
unbounded precision and unbounded computation. Performance is a separate, empirical
question, and where it has been measured the two diverge: networks with ample capacity to
fit their training data still fail to generalize across the Chomsky hierarchy
\citep{deletang2023chomsky}, and frontier models that could in principle decompose a
compositional problem instead rely on shortcut pattern-matching and degrade as it grows
\citep{dziri2023}. We therefore treat realized capability as a hypothesis to be measured,
not inferred from expressive power.

\theme{complexity hierarchy}Measuring it requires a principled notion of what makes one
processing task harder than another, and formal language theory provides one. The
Chomsky hierarchy \citep{chomsky1956} ranks a language by the machinery its recognizer
needs. A \emph{regular} language can be read with finite state alone---a regular
expression; a \emph{context-free} language needs a stack, to follow nesting and
recursion; a \emph{context-sensitive} language must enforce agreement or counting
across the whole input, as in ``declare $N$ items, then produce exactly $N$,'' which no
stack alone can do; and at the top, \emph{recursively enumerable} languages allow
arbitrary and possibly non-terminating computation.

\theme{mildly context-sensitive}Because the jump from context-free to context-sensitive
is so wide, a finer band was singled out between them---Joshi's
\emph{mildly context-sensitive} languages \citep{joshi1985} and the LCFRS fan-out
ladder \citep{seki1991}---which captures bounded counting and cross-serial
dependencies while still parsing in polynomial time. It is also the band into which
most of the real scientific output we study falls (\S\ref{sec:prelim}).

\theme{grammar-availability}Grammatical class is only half of what makes a format hard
in practice. The other half is whether a grammar is actually \emph{available}---whether
someone has already designed and tested a parser for it---and this second factor can run
counter to the first: a context-free XML file is grammatically more complex than a
regular, ad-hoc log, yet far easier to extract, because its grammar has been supplied.
Separating intrinsic class from grammar-availability allows a success or failure to
be attributed to the correct cause; the harness acts on the second factor, not the
first.

\theme{parsing as probe}Parsing is a well-suited probe for this gap. It
is the first step of nearly every information-processing chain and among the least examined,
yet on real inputs it already spans the whole hierarchy, from trivially regular tables
to cross-referential multi-file formats. The nearest prior measurements grade language
models on formal-language recognition across the Chomsky hierarchy as input length
grows \citep{chomskybench, relic}. These are the closest prior work, but they measure a
different task: they use synthetic strings and ask the model to \emph{recognize}
membership, whereas we use real, heterogeneous scientific output and ask the agent to
\emph{build a working
artifact}---a parser or extraction pipeline that returns correct structured data. And
instead of a single accuracy number, we vary the support the agent is given and index
its failures by grammatical class, so as to identify not only where performance degrades
but the associated failure modes and the conditions that recover it.

\theme{test case}The output we parse is real computational-chemistry data: the logs
and restart files that ab initio simulations produce. They are a demanding instance:
heterogeneous across codes, weakly standardized, and dense with the counting
and cross-reference structure that occupies the middle of the hierarchy. A silent
parsing failure here becomes a silent \emph{scientific} failure, as the downstream
analysis is then grounded on no data.

\section{The system under test: an MCP parser harness}

By a \emph{parser harness} we mean a layer that wraps a collection of independently
developed parsers behind one uniform interface---with documentation and machine-readable
metadata---so that a caller can discover which parser handles a given format, select it,
and invoke it without re-implementing the parsing itself. The instrument for this study
is one such harness\ifblind\else, \emph{Parse Patrol}\fi: a dual-mode scientific parsing
framework built on the Model Context Protocol (MCP)~\citep{mcp}, first released as
\ifblind an open-source project\else part of a community hackathon on language-model
applications in materials science and chemistry~\citep{hackathon2025}\fi.
It wraps a set of existing, independently maintained community parsers (plus, for this
study, a coarse regex parser standing in for regex-class tools) and exposes each
of them in two ways: as an MCP tool that an agent can discover and call
interactively, and as a direct Python import that a production pipeline can depend on. Both exposures return
the same Pydantic-validated output model, so the data contract is identical whether a
parser is called as a tool or imported.
Around the parsers sits a documentation layer---per-parser descriptions of the formats
each one handles, the schema of that output model, machine-readable capability metadata,
and prompt scaffolding.

\ifblind The harness\else \emph{Parse Patrol}\fi was conceived to serve parser
\emph{onboarding} into \ifblind a \textsc{fair} materials repository\else NOMAD~\citep{draxl2019nomad}\fi,
which ingests the outputs of dozens of simulation codes and relies on a
hand-written, tested parser for each one. Onboarding a new code is therefore gated on
someone authoring and validating that parser---a slow, manual, and easily-stale
bottleneck. The harness targets it directly: it automates the testing and deployment of
parsers as they are contributed, so a new parser is checked against real files and made
discoverable rather than re-implemented. Its broader aim is to turn parsers into shared,
tested, discoverable community components, so that parsing capability---and with it the
machine-readability of scientific output---is exchanged across the community rather than
rebuilt in isolation each time~\citep{ghiringhelli2023metadata}. Exposing those same
components to coding agents, the setting we study here, is a natural extension of that
goal.

This layered design also makes the framework a clean measurement instrument. Because the
parsers, their documentation, and their tool exposure are separable, we can give the agent
any subset of them while holding everything else fixed---varying how much the harness
provides and measuring the effect on what the agent produces.

\section{Method}

\theme{two axes}The experiment varies difficulty along two axes. The first is
the \emph{source}: the grammatical class of the format being read---regular,
context-free, mildly context-sensitive, or context-sensitive---held apart from
grammar-availability, so that having or lacking a tested parser is measured as its own
factor rather than folded into the class. The second is the \emph{target}: how hard the artifact
the agent must \emph{produce} is. This is a generation problem, not a recognition one,
and is therefore not a second instance of the Chomsky hierarchy: the output's
surface syntax (a JSON object, a Python script) is cheap to emit and, if re-parsed
downstream, cheap to recognize. What scales here is \emph{semantic} correctness: a
bounded target (fill a fixed schema) has a finite, field-checkable output space,
whereas a Turing-complete target (generate an executable artifact such as a PySCF input
script) has an unbounded one whose correctness is undecidable in general. Source
difficulty is thus a question of \emph{recognition} (the Chomsky hierarchy), target
difficulty a question of \emph{synthesis} and verifiability---two distinct axes.

\theme{arms}We vary how much of the harness the agent receives. In every arm
it is given the source file, the target schema, and the ability to run code; the arms
differ only in the support layered on top. At one extreme (\textsc{none}) the agent
gets no harness at all and must write its parser from scratch. From there we add
support one layer at a time: exposing the parsers as callable tools but nothing more
(\textsc{bare}), then adding their per-parser documentation (\textsc{docs}), then a
cross-parser capability map of which tool recovers which property (\textsc{full}), and
finally an annotation of the source's grammatical class together with each tool's
parsing-power ceiling (\textsc{complexity}). The step from \textsc{none} to the rest
isolates the value of the harness itself; the steps among the remaining arms isolate
the value of the documentation built on top of it.

\theme{instrumentation}All runs use a single coding agent (Claude Opus 4.8) driven
through the Claude Agent SDK, with identical task prompts and per-run turn and budget
caps; only the arm's system-prompt support differs. Per run we record tool calls, turns,
tokens, the agent's \emph{chain-of-thought}, and a failure-mode taxonomy scored by
conservative, transcript-grounded detectors (wrong-parser, silent-empty-accepted,
parser-from-scratch, unit-error, retry-loop, gave-up), indexed by grammatical class
$\times$ arm. Correctness is scored field-level against a reference built from the union
of succeeding parsers.

\section{Results}

\subsection{Preliminary: the grounding layer and the grammar-availability effect}
\label{sec:prelim}

Our test corpus is 1{,}104 real output files spanning 16 simulation codes, drawn from a
public computational-materials database~\citep{draxl2019nomad} whose persistent
identifiers let each file be traced. By grammatical class it is heavily skewed toward the
middle of the hierarchy: of the primary-output files, 44 of 51 are mildly
context-sensitive free-form logs and only four are context-free formats with a supplied
grammar. The two extremes below Turing-completeness are barely present---none is purely
\emph{regular} (Chomsky type~3, finite-state) and only three are \emph{context-sensitive}
(type~1, cross-referential multi-file), too few to test. Our measurements therefore speak
to the middle two rungs, which are also the common case for real ab initio output; we
return to the extremes in the outlook.

As a component measurement motivating the axes, we ran the four wrapped parsers
themselves---three maintained community libraries plus a coarse regex parser standing in
for regex-class tools---directly on these files, scoring whether an atomic structure was
recovered (Table~\ref{tab:rel}). Each parser targets only a few of the codes, so no single
one recovers structure from more than a quarter of the primary-output files---low by
specialization, not by defect. Even a best-of-four selector that accepts \emph{any}
parser's output, i.e.\ an upper bound on what routing among them could achieve, recovers only \(45\%\): the
available parser set collectively covers under half of this heterogeneous space. Its
failures are often \emph{silent}---the parser returns grammatically well-formed output
that is nonetheless void or semantically corrupted, raising no exception. This measures
the wrapped tools; the agent-generated code, which need not rely on any single parser, is
the subject of \S\ref{sec:main}.

Re-cut by grammatical class (Table~\ref{tab:class}), best-of-four recovery is \(100\%\) on
the context-free formats and \(43\%\) on the mildly context-sensitive logs. The gradient
tracks grammar-availability rather than class as such: the context-free formats, though
grammatically more complex, are recovered whenever a supplied grammar exists, whereas the
plainer free-form logs without a canonical grammar are not. A supplied grammar, not
grammatical simplicity, appears to drive extraction reliability.

\subsection{Main: realized capability and failure modes by arm}
\label{sec:main}

We compare all five arms on an identical set of 30 tasks (Table~\ref{tab:main} for
success, Figure~\ref{fig:fail} for failure modes; the single context-sensitive task is
held out). These are observations from a first sweep, not confirmed effects: single runs
per cell and one model preclude significance claims, and per-run results and
chain-of-thought transcripts appear in the appendices. Three results stand out; success
does not rise monotonically with harness support.

\emph{(O1) Exposing tools barely moves success but adds cost and silent failures.} From
\textsc{none} to the plain tool arms, total success rises only modestly (53\% to
60--63\%), while average tool calls \emph{rise} (5.4 to 7.4) and two failure modes appear
that the from-scratch baseline never exhibits: wrong-parser calls (0 to $\sim$21) and,
more troubling, silent-empty outputs (0 to $\sim$11), where the agent accepts an empty
parse and emits a hollow result with no error. Per-parser documentation
(\textsc{docs}, \textsc{full}) does not remove these.

\emph{(O2) The complexity annotation is what shifts the failure profile.} \textsc{complexity}
attains the same success as \textsc{full} (63\%) but nearly eliminates the interface
failures---wrong-parser $21\to2$, silent-empty $11\to1$---and returns effort to
near-baseline (5.9 tool calls). Telling the agent where the source sits on the hierarchy
and where each tool's power tops out, rather than merely which formats each tool
nominally supports, appears to be the operative ingredient.

\emph{(O3) Reasoning failures are untouched.} The gave-up rate (missing core fields) is
essentially flat across every arm (11--14), including \textsc{none}, and no harness
variant we tested changed it.

\section{Discussion and outlook}

At the tool level, these first sweeps read as feedback on the harness rather than the
agent: the mismatches above are a failure of tooling, not of the agent, which merely acts
on the unreliable or overstated information it is given. These tests also expose two
structural shortcomings in the MCP server itself. First, its capability metadata
overstates which formats each parser handles, so
an agent that trusts it calls a parser that returns nothing. Second, its Pydantic output
contract is permissive enough that a hollow parse validates as a well-formed object,
leaving the emptiness silent. Both are addressable---through tighter capability
descriptions and stricter output constraints (required fields, non-empty collections,
cross-field consistency)---and are slated for correction before the next round of
tests. The semantic gap runs
deeper: confirming that a non-empty, internally consistent result holds the \emph{correct}
values exceeds what a permissive type contract can express, and may demand a more
expressive discipline than Python affords---dependent types, for instance---or validation
outside the type system altogether.

The larger effect is the opposite. What most improved the agent's behaviour
was not more tooling but \emph{knowledge}: a short statement of where the source sits in
the language hierarchy, and where each tool's power ends, collapsed the interface failures
at no extra cost. Why this context helps, and how the agent uses it, is best read from the
chain-of-thought; extending coverage to the multi-file (context-sensitive) case is the
next step. The Turing-complete extreme, by contrast, amounts to code analysis
and is already well studied elsewhere---a known bound rather than a target for this line.

\section*{Limitations}

This is a first, small study and its numbers are indicative, not conclusive. The agent
sweep uses a single model (Claude Opus 4.8), a single target schema, and one run per
cell, so we make no significance claims and cannot separate model-specific behaviour from
general effects. The corpus is a single database snapshot (51 entries, 16 codes) heavily
skewed toward the mildly-context-sensitive band, and the \textsc{complexity} arm bundles
two cues---the source's grammatical class and each tool's power ceiling---that the design
does not separate. Further methodological caveats---the
union-of-parsers reference in place of independent ground truth, the heuristic failure
detectors, and the infrastructure exclusions---are detailed in the appendix.

\section{Experimental detail}\label{app:setup}

The harness and experiment code, anonymized for review, are available at
\url{https://anonymous.4open.science/r/parse-patrol-C611/}.

Each run gives one coding agent (Claude Opus 4.8, via the Claude Agent SDK) a single
source file, the fixed target schema, and code execution, capped at 30 turns and a
per-run spend budget; only the arm's system-prompt support varies, as described in the
Method. Success is field-level agreement with a reference built from the union of all
succeeding parsers on that file rather than an independent ground truth, and the
failure-mode labels come from conservative, transcript-grounded detectors; both are
therefore approximate, and a run is counted toward a mode when it \emph{exhibits} that
mode (a successful run may still have made, e.g., a wrong-parser call en route). The
grammatical-class assignment is a documented ordinal, partly confounded with program at
the small per-class sample sizes.

The 16 simulation codes spanned by the corpus are ABINIT, CASTEP, CP2K, Crystal,
exciting, FHI-aims, GAMESS, Gaussian, GPAW, LAMMPS, NWChem, Octopus, ONETEP, ORCA, VASP,
and WIEN2k. Three GAMESS tasks, whose parsed model exceeds the agent runtime's
message-size limit, and one $\sim$3.5\,GB GPAW output, which hangs the run, are excluded
from the agent sweep---infrastructure constraints, not parsing outcomes.

\section{Representative chain-of-thought}

The contrast is visible in the transcripts. On a CASTEP log (hard, no supplied grammar),
the \textsc{bare} agent follows the tool affordance---``CASTEP is best handled by
[two parsers]; let me parse with both''---then ``both parsers failed,'' and proceeds to
emit a partly-empty result. The \textsc{complexity} agent, told the source is a free-form
log outranking every available parser, skips the tools and reads the file directly
(``this is a CASTEP single-point energy calculation; let me compute the conversions and
write the output''). The difference is not capability---both can read a file---but knowing
in advance that the tools will not fit.
